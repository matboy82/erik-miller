# PRD: Miller Remodeling — Website + Lead Qualification System

> **Status: Approved — Matt, 2026-10-01.** Built from the approved project scope; structured for systematic build under the BIS AI-First Development System (spec → implementation → QA → code review → adversarial review → stakeholder review → release authorization → production verification).
>
> **Commercial:** pro bono in exchange for testimonial. **Client:** Erik Miller, Miller Remodeling LLC (Eagle, ID).

## 1. Background & Problem

Miller Remodeling has 25 years of craft, a systematized kitchen/bath process, and an in-house designer — but the front of the business is a phone number and unpaid design work. The current site is a 2-page WordPress brochure: zero forms, phone-only contact, stale since 2025-01-03. Every serious prospect costs Erik hours of free design before he knows if they can buy.

Erik's target model: **8 x $100k / 3-month jobs** instead of 33 x $30k drive-bys, with a **paid design process** sold up front. The system we build must: attract the right prospects, qualify them (budget/timeline/fit/photos) *before* Erik's time is spent, sell the design phase, feed everything into his JobTread CRM, and turn every finished job into reviews and content automatically.

**Positioning constraint (Matt, 2026-10-01):** no WordPress, no theme-and-plugin stack. Custom static-first rebuild on BIS-owned infrastructure; intake via a BIS-built API. We are not a bargain plugin shop.

## 2. Goals & Success Metrics

| # | Erik's goal | Measurable success criterion |
|---|---|---|
| 1 | Professional website | Lighthouse ≥ 90 (perf/accessibility/SEO), LCP < 2.5s, live on BIS-managed infra |
| 2 | More leads, better qualified | 100% of inquiries captured in JobTread with fit brief + photos; ≥ 60% of wizard completions are in-service-area, budget-qualified |
| 3 | Close rate > 35% | Design-consult → signed design agreement rate tracked; baseline established at launch, > 35% target on design-ready leads |
| 4 | Proactive scheduling + lead info incl. photos | Qualified prospects can book a design consult from the wizard; every JobTread lead carries description + photos |
| 5 | Job writeups: before/after/video | Repeatable per-job capture flow; ≥ 1 published portfolio entry per completed job |
| 6 | Automated review process | JobTread Workflows review request fires on every job completion; site testimonial layer updates via approval gate |
| 7 | Content strategy from completed work | Portfolio → GBP/social pipeline documented with a cadence Erik can sustain |

## 3. Users & Stakeholders

- **Prospect** (homeowner in Treasure Valley): discovers via search/AI/referral, qualifies themselves via wizard, books a design consult.
- **Erik Miller** (owner/operator): receives fit briefs in JobTread, approves reviews, captures job writeups with his phone.
- **Erik's in-house designer**: executes the paid design phase (selections/floorplans/3D walkthroughs).
- **Matt / BIS**: builds, hosts, maintains; stakeholder reviewer at every gate.

## 4. System Architecture (target)

```text
Prospect → Static site (Astro 7 + React islands, BIS-hosted — see ADR-2026-10-01-Miller-Remodeling-Frontend-Stack)
             ├─ Qualification wizard (frontend)
             │     └─ POST → BIS Intake API (we own it)
             │               ├─ Fit scoring (rule-based)
             │               ├─ JobTread Pave API: createAccount → createJob
             │               │    (+ customFieldValues, presigned-URL photo uploads)
             │               └─ Notify Erik (email/SMS)
             ├─ Design-consult booking (embedded scheduler on thank-you page)
             └─ Portfolio / testimonials / service + city pages (static, schema.org)

JobTread (Erik's CRM, system of record)
             └─ Workflows: job complete → survey + review request (native)
             └─ Approval gate → published reviews feed the site testimonial layer
```

**Key decisions (locked):** no WordPress; no Zapier/Make as a build dependency (fallback only); JobTread is the system of record (no CRM decision needed); secrets (JobTread grant key) server-side only, never in the repo or client bundle.

## 5. Workstreams

Each workstream is a buildable epic: it enters implementation only after its spec (intent, scope, acceptance criteria, constraints, dependencies, risks) is accepted per the AI-First Development System gate 1.

### WS-0 — Project scaffolding & infrastructure

**Intent:** a clean, BIS-owned foundation everything else builds on.
**Scope:**
- **Monorepo** (single repo, Matt's call 2026-10-01): `apps/web` (Astro site) + `apps/worker` (intake API) + shared `packages/` as needed. One CI pipeline, one checkout for Codex.
- Repo setup (BIS GitHub; branch strategy; CI: build, lint, typecheck, `astro check`, Lighthouse CI).
- Hosting + deploy pipeline on Cloudflare Pages (locked 2026-10-01) + Workers for the intake API.
- **Live test URL from day one** (Matt's call 2026-10-01): a persistent `test` deployment (e.g. `test.millerremodelingidaho.com` or the Pages-assigned URL) where Erik can watch progress live. `main` → test URL; production domain cutover is a separate, explicit release decision (WS-9).
- **Fast Worker spike:** deploy a hello-world Worker on day one to prove the Pages + Worker + CI pipeline end-to-end before any real endpoints are built (WS-2 builds on it).
- **Placeholder policy** (Matt's call 2026-10-01): where a third-party account doesn't exist yet (Google Workspace, Calendly, Zoom, etc.), ship a clearly-marked placeholder component/section and keep building — never block on account provisioning. Every placeholder is registered in a `PLACEHOLDERS.md` at the repo root with owner + unblock condition; nothing ships to production with an open placeholder unresolved.
- **Design-review toolbar (test URL only)** (Matt's call 2026-10-01): a floating toolbar, rendered **only on the test deployment** (env-gated, stripped from the production build), that lets Erik compare directions live:
  - **Theme switcher:** A / B / C from the branding kit — swaps the full token set via `data-theme` on `<html>` (+ `localStorage` persistence). All three `:root` token blocks ship on the test build; production ships exactly one.
  - **Content switcher:** variant selector for key copy — tagline candidates and hero/process copy variants (defined per direction in the branding kit) — so Erik reacts to words and look together.
  - The toolbar is visually unmistakable as a review tool (not site chrome). WS-9 acceptance: it does not exist in the production build.
- DNS plan for millerremodelingidaho.com (registrar: Porkbun — credentials held by Matt); cutover runbook.
- Analytics baseline (carry over GA or lightweight alternative — decide in spec).
- Secrets management (JobTread grant key + notification credentials in env/secret store; never committed).
- ADR locked 2026-10-01 (Matt): Astro 7.x pinned + React islands + TypeScript, static output; **hosting locked: Cloudflare Pages** (BIS-owned account, DNS stays at Porkbun) — see `08-Technology/ADRs/ADR-2026-10-01-Miller-Remodeling-Frontend-Stack.md`. Conventions for Codex: `client:visible` default for below-fold islands; content via Content Layer API with Zod schemas; `astro check` in CI. Remaining open: analytics choice; intake API hosting (leading candidate: Cloudflare Worker, decided in WS-2 spec).
**Acceptance:** monorepo builds via one command; empty site live on the test URL via CI; hello-world Worker responding on its route; preview deploys per PR; design-review toolbar (theme + content switchers) working on the test URL and **provably absent** from a production build; `PLACEHOLDERS.md` exists with the first entries (scheduler, any missing accounts); secrets load from secret store; DNS cutover runbook reviewed.
**Constraints:** no WordPress; no committed secrets.
**Dependencies:** Porkbun access (have), hosting account decision (Matt).
**Risks:** DNS cutover downtime — mitigate with low-TTL + runbook + off-hours cutover.

### WS-1 — Foundation site rebuild (Phase 0)

**Intent:** a professional, fast site that proves craft and captures inquiries.
**Scope:**
- Design system: professional, understated (per Matt's virtual-background-era taste: clean, not flashy); mobile-first; WCAG 2.1 AA.
- Pages: home, kitchen remodels, bathroom remodels, whole-home remodels, additions, ADU/mother-in-law, home repair; service-area pages (Eagle, Star, Meridian, Boise, Middleton, Kuna); about/process; portfolio index; contact.
- Copy: rewritten around proof + process (replace "A passion for creating spaces" brochure copy); design-phase positioning baked in.
- Testimonial layer seeded from existing reviews (Chamber 5.0/11 quotes; GBP confirmation pending).
- SEO/AI-citation: `GeneralContractor` + `Review` + `Service` schema, FAQ schema, sitemap, robots, canonicals; 301 map from old WP URLs.
- Working contact path (name/phone/email/message → intake API → JobTread, flagged as general inquiry).
- Measurement: inquiry events tracked end-to-end.
**Acceptance:** Lighthouse ≥ 90 across categories on mobile; LCP < 2.5s; all pages render with valid schema (Rich Results test); 301s verified; end-to-end contact test creates a JobTread record; Erik approves design (stakeholder review).
**Constraints:** content depends on Erik's project descriptions + photos (in progress) — build with placeholder content strategy that doesn't block launch.
**Dependencies:** WS-0; WS-2 (contact path needs intake API).
**Risks:** content delay — mitigate with staged launch (site live, portfolio fills as content arrives).

### WS-2 — Intake API (BIS-owned)

**Intent:** the single backend for all lead capture; the anti-plugin.
**Scope:**
- Builds on the WS-0 hello-world Worker — real endpoints land on infrastructure that's already proven live.
- `POST /intake/lead` — validates wizard payload (incl. photo uploads), runs fit scoring, calls JobTread Pave `createAccount` (type: customer) → `createJob` with `customFieldValues`, uploads photos via presigned-URL flow, notifies Erik.
- `POST /intake/contact` — lightweight path for the general contact form.
- Idempotency keys on submissions (no duplicate JobTread records on double-submit).
- Rate limiting + spam protection (honeypot/CAPTCHA decision in spec) + input validation.
- Structured logging; dead-letter/retries for JobTread outages (lead never lost: persist-then-forward).
- OpenAPI spec for the endpoints.
**Acceptance:** contract tests against Pave (or recorded fixtures); double-submit creates one JobTread customer; JobTread outage → lead persisted and retried, Erik notified of delay; no secret leaks in logs; adversarial review passes.
**Constraints:** grant key server-side only; PII handling documented.
**Dependencies:** JobTread API confirmation against official explorer with Erik's login (open decision #5); WS-0.
**Risks:** Pave API behavior differs from community docs — mitigate with early spike (pre-build verification call) before WS-3.

### WS-3 — Qualification wizard (frontend)

**Intent:** ask the awkward questions so Erik doesn't have to; output a fit brief.
**Scope:**
- Multi-step wizard: project type → location (service-area check) → timeline → budget range → description + **photo upload** → built-before/how-found → contact details.
- Rule-based fit score (in-area, budget band, timeline, project-type match) + human-readable fit brief.
- Branching: low-fit (out-of-area / repair-only / budget mismatch) → polite redirect with alternatives, still captured to JobTread as low-fit (Erik sees everything).
- Qualified path → thank-you page with design-consult booking (WS-4) + "what happens next" expectations (paid design phase explained).
- Mobile-first UX; progress saved locally; accessible.
**Acceptance:** full happy-path creates a JobTread customer+job with all custom fields + photos attached; low-fit path redirects correctly and still logs; validation errors are clear; works with JS disabled to the extent of a fallback form (decide in spec); Erik walks the wizard in a 30-min session and signs off on the questions.
**Constraints:** questions finalized with Erik (30-min session); budget bands set by Erik.
**Dependencies:** WS-2.
**Risks:** over-asking drops completion — mitigate with progress indicator, minimal required fields, analytics on drop-off steps.

### WS-4 — Design-consult scheduling

**Intent:** proactive scheduling — qualified prospects book without phone tag.
**Scope:**
- Embedded scheduler on the wizard thank-you page (Calendly or equivalent — decision in spec; must support buffers, no double-booking, timezone handling). **If no scheduler account exists yet: ship the placeholder section** (per WS-0 placeholder policy — e.g. "Online booking coming soon — call/text 208.608.4439"), register it in `PLACEHOLDERS.md`, and wire the real embed when the account exists. Never blocks the wizard launch.
- Booking confirmation + reminders (email/SMS); cancellation/reschedule links.
- Booking writes back to JobTread (appointment on the job/customer).
- Design-phase fee + package displayed at booking (Erik sets — open decision #2).
**Acceptance:** test booking appears in Erik's calendar and in JobTread; reminders fire; cancellation works; no double-booking under concurrent attempts.
**Constraints:** Erik's availability rules; fee display copy approved by Erik.
**Dependencies:** WS-3; scheduler account decision (Matt).

### WS-5 — Job writeup pipeline (portfolio CMS flow)

**Intent:** every finished job becomes proof, with minimal effort from Erik.
**Scope:**
- Repeatable capture flow: per job — writeup (scope/challenges/result), before pics, after pics, finished-product video.
- Lightweight CMS/collection flow Erik can operate from his phone (decide: Git-based CMS, headless CMS, or structured form → PR; spec decides).
- Portfolio entry template: story + gallery + video + location/project-type tags + review cross-link.
- Publishing flow: draft → Erik approval → publish (stakeholder review per entry, lightweight).
**Acceptance:** Erik can publish a portfolio entry from his phone in < 15 minutes (timed walkthrough); entries render with gallery + video + schema; approval step enforced.
**Constraints:** must be operable by a non-technical owner.
**Dependencies:** WS-1 (portfolio index).

### WS-6 — Automated review flow

**Intent:** reviews happen automatically; the site stays fresh.
**Scope:**
- Configure JobTread Workflows "Project Completion Wrap-Up": job complete → customer survey + Google review request.
- Approval gate: new reviews held for Erik's approval before publishing to the site testimonial layer (auto-publish after N days if no response — decision in spec; default: hold).
- Review request timing + copy (Erik approves).
**Acceptance:** marking a test job complete fires the sequence; review link works; approval gate holds publishing; published review appears on site.
**Constraints:** review platform policies (no incentivized reviews); Erik owns the approval.
**Dependencies:** JobTread access (have); WS-1 (testimonial layer).

### WS-7 — Content engine (bonus)

**Intent:** completed work becomes marketing on a cadence Erik can sustain.
**Scope:**
- Documented pipeline: portfolio entry → GBP post → Facebook/Instagram posts (copy templates per project type).
- Quarterly case-study format for SEO ("kitchen remodel Eagle ID" style pages).
- Cadence + ownership doc (what Erik does per job vs. what BIS/automation does).
**Acceptance:** pipeline doc reviewed by Matt; one full pass executed on a real completed job (portfolio → GBP → social).
**Constraints:** Erik's sustained effort must be < 30 min per job.
**Dependencies:** WS-5, WS-1.

### WS-8 — AI-visibility layer

**Intent:** be findable where buyers look now (search + AI assistants).
**Scope:**
- Structured business data (Organization/GeneralContractor, service area, sameAs links), FAQ content, AI-assistant-readable files.
- Google Business Profile consistency + review link surfaced; directory consistency check.
- Baseline measurement (branded + "remodeler Eagle ID" style queries; AI-assistant citation checks) + quarterly re-measure.
**Acceptance:** baseline recorded; Rich Results valid; GBP linked and consistent.
**Constraints:** honest expectation — compounds over months, not days (stated in scope).
**Dependencies:** WS-1.

### WS-9 — Launch, QA & handover

**Intent:** ship through the gates, not around them.
**Scope:**
- QA plan per workstream executed (happy paths, failure modes, integration behavior, security, rollback).
- Code review + adversarial review records per workstream.
- Stakeholder review: Erik walkthrough + sign-off per phase (Phase 0 site; Phase 1 wizard + flows).
- Release authorization + DNS cutover; production verification (real inquiry end-to-end on the live domain).
- Handover: Erik's runbook (how to approve reviews, publish portfolio entries, read JobTread briefs); BIS maintenance note.
- Testimonial capture (per commercial terms — timing/format per open decision #4).
- **Design-direction lock:** Erik's theme pick recorded (ADR amendment); production build contains exactly one token set; the design-review toolbar verified absent from production (no `data-theme` switching code, no extra token blocks, no toolbar markup in the served HTML).
**Acceptance:** all gates evidenced; production verification passes on the live domain; Erik's runbook delivered; testimonial captured.

## 6. Non-functional requirements

- **Performance:** Lighthouse ≥ 90 (perf, a11y, SEO, best practices); LCP < 2.5s on mobile; no render-blocking third-party bloat.
- **Security:** OWASP basics — validated inputs, rate limits, secrets in secret store, least-privilege JobTread grant key, no PII in logs, HTTPS everywhere, security headers.
- **Accessibility:** WCAG 2.1 AA.
- **Maintainability:** typed codebase, documented ADRs, CI on every PR; Erik-touchable surfaces (WS-5/WS-6) require zero code.
- **Observability:** intake API structured logs + alerting on failures; JobTread sync health visible.

## 7. Out of scope

- Paid ads management; full SEO retainer (baseline + structure only).
- JobTread configuration beyond the integration (Erik's instance stays his).
- The design phase itself (Erik + his designer deliver it — we sell it, we don't do it).
- Video production (Erik captures; we publish).
- Native mobile app.
