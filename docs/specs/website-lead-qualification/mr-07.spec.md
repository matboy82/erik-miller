## Intended change and interfaces

Add a multi-step qualification page that produces an explicit typed lead payload accepted by MR-05's server boundary. Fields cover project type, location, timeline, budget, description, photos, prior-building experience/referral source, and contact. The response exposes only receipt/delivery state and a safe next step. Keep fit rules as a versioned, testable pure decision boundary using Erik-approved inputs; return a human-readable brief while keeping internal score details private.

Use a progressive enhancement path: server-rendered explanatory content and a usable fallback form, with a focused React island for progress and branching (`client:visible` only if below the fold). Save only non-sensitive step selections in local storage; never persist contact data, description, or photos there. Provide an explicit clear action. Do not finalize question text, thresholds, required fields, or low-fit alternatives without Erik's approved values.

## Data, privacy, and quality

Accepted 0006 governs the short-lived ledger, duplicate control, async JobTread delivery, and photo staging. Validate at the Worker boundary, enforce upload type/size, remove image metadata where supported, and expose progress without PII. Do not send a success confirmation until durable acceptance. Preserve all qualified and low-fit leads in JobTread with the decision/rule version.

Use existing Astro/React/TypeScript conventions and pinned mobile Lighthouse and WCAG 2.1 AA protocols. No analytics vendor is selected; any event instrumentation must be privacy-approved, aggregate/minimal, and exclude field values/PII.
