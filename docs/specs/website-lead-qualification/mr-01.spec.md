## CI and deployment contract

Verification runs on `main` pushes and `pull_request`, with read-only repository permissions and no Cloudflare secrets. Keep `npm ci`, `npm run check`, and `npm run lighthouse` before publishing. Do not use `pull_request_target` to build PR code. Check out the same event revision in verification and deployment; record the PR head and tested merge revision separately when applicable.

| Event/state | Pages result | Worker result |
|---|---|---|
| Disabled deployment, failed/cancelled/skipped verification, or fork PR | No publication or deployment secrets | No publication |
| Enabled, authorized, passing `main` push | Persistent test project's `main` branch | Test health Worker |
| Enabled, authorized, passing same-repository PR | Preview branch `pr-<number>`, distinct from `main` and other PRs | No deployment |

Use GitHub environment `test`, existing secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, repository variables `CLOUDFLARE_PAGES_PROJECT` and `ENABLE_TEST_DEPLOYS`, and existing Worker `miller-remodeling-intake-test`. Default project is `miller-remodeling-test`; Matt confirms the intended BIS account/repository/project before enabling deployment. Reject missing configuration before upload. Keep secrets out of installation/build steps; expose them only to the upload/deploy steps. Same-repository contributors are a trusted boundary; Matt configures required environment approval when repository access does not justify that trust.

Build the review site in the secret-free part of the deployment job using the same revision and lockfile. Deploy through the pinned local Wrangler CLI. Pass computed preview names as quoted arguments, never executable branch text. Serialize persistent Pages/Worker deployments without cancelling a running publication; verify the current `main` revision before publishing to avoid an older queued run overwriting a newer one. PR concurrency is separate per PR.

Record sanitized deployment URLs and revision in the run summary/evidence. A partial Pages/Worker deployment or failed live check fails the deployment job; report each resource's outcome. No automatic claim of atomic deployment or readiness is allowed.

## HTTP and secret boundaries

Keep HTML robots meta, `robots.txt` disallow, and Pages `_headers` noindex for review builds. Check actual persistent and preview HTTPS URLs after publication; no business-domain attachment is permitted. Noindex is indexing policy, not access control: the test scaffold must contain no private stakeholder or customer material.

Preserve `worker.fetch(Request)` behavior: GET `/health` returns HTTP 200 and the existing scaffold JSON with `Cache-Control: no-store`; HEAD has no body, unsupported methods return 405, and unknown routes remain 404. No database, runtime credential, or new endpoint is introduced.

Keep Cloudflare credentials and lead PII out of source, fixtures, client output, and retained logs. Use harmless sentinels to prove client-bundle isolation and inspect the complete output tree. Do not print real secret values to test masking. Configuration names and redacted outcomes are sufficient evidence.

## Required quality bar and verification

Pin the approved QA mobile protocol, 2026-10-01 branding kit, candidate revision/dirty diff, lockfile, and Lighthouse config. Existing three-run mobile LHCI measures review `/` starting at A. Preserve its current optimistic aggregation and make that setting explicit: category assertions use the best score; LCP uses the minimum numeric value across the three valid runs. Scores must be ≥ 0.90 for performance, accessibility, and best practices; SEO stays warning-only.

Aggregation follows the installed `@lhci/utils` assertion behavior and [official LHCI configuration reference](https://googlechrome.github.io/lighthouse-ci/docs/configuration.html), read 2026-10-01. Record all individual results so the aggregation does not hide variability.

Keep the existing LHCI LCP assertion and add a strict report check to `npm run lighthouse`: the same aggregated LCP must be finite and **< 2500 ms**. Equality fails. Require three valid reports for the expected page; missing, malformed, wrong-page, or incomplete reports fail rather than silently passing. Retain individual reports, assertion output, and the strict result. Test values below, equal to, and above 2500 independently of browser variability. No new browser framework or public measurement interface is selected.

| QA / story coverage | Evidence and seam |

| F1 / AC1 | Isolated fresh checkout, Node/npm/Chrome/Lighthouse versions, OS and effective mobile viewport/throttling, exact revision, command logs/exit codes, LHCI reports and settings. Run `npm ci`, `npm run check`, `npm run lighthouse`. Never reset the user's checkout. |

| F4 / AC6 | Setup/config name agreement, sentinel build checks, sanitized source/output/log inspection, environment/token scope evidence, and exact placeholder unblock evidence. |

Use existing Node `node:test` suites and command/output boundaries. Follow vertical red-to-green cycles for missing behavior. Prove sensitivity of deployment restrictions and credential/output checks with restored temporary mutations or equivalent negative controls. Existing passing health behavior needs no artificial red test. Record absent Chrome, missing access, incomplete reports, or unavailable live evidence as unverified. Automated accessibility scores do not establish WCAG conformance.
