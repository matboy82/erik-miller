## Decisions for approval

- Keep the existing Astro toolbar and small review script; add no React runtime or browser automation dependency for these controls.
- Separate visual direction, copy direction, and tagline choice. A theme change starts with its matching copy set; reviewers can then select another copy set or tagline without changing the theme.
- Validate one versioned brand lock against a recorded Erik choice and its Accepted decision record. Environment variables cannot replace approval.
- Select production inputs before rendering and exclude alternatives from every shipped file, including unused fonts and copied assets. Disposable fixtures exercise the same selection and validation rules without changing the real lock.

The [accepted frontend stack](../../architecture/decisions/ADR-2026-10-01-Miller-Remodeling-Frontend-Stack.md) and [0001 reconciliation](../../architecture/decisions/0001-bootstrap-foundation.md) govern the stack. Accepted [0002](../../architecture/decisions/0002-test-deployment-isolation.md) governs hosting and publication. New 0003 is required because the production approval and isolation policy is a durable compatibility/rollout decision. It selects a mechanism, not Erik's brand. Classify this work Medium blast radius because it changes a shared build gate; record code-review and a fresh-session adversarial verdict in `mr-02.review.md` before release planning.

## Review-page contract

Use the [branding kit](../../brand/branding-kit-2026-10-01.md), edition 2026-10-01, sections 5, 10, and 12 as the comparison reference. Keep typed brand data separate from rendering. Each direction owns its complete palette, semantic colors, display/body font pairing, and four existing copy fields: tagline, headline, description, and process header. Expose the five section-2 tagline candidates plus C's section-12 tagline, with stable IDs rather than stored display strings. Retain the existing process steps and working phone link. CTA/trust-line copy for future sections does not add those sections or imply working booking in this story.

Apply the entire direction to the page: background, text, surfaces, accents, display font, and direction-appropriate headline/kicker treatment. Retain all specified palette values, assigning low-contrast colors to decorative roles where necessary. Compare actual computed styles and text rather than treating presence of an unused token as coverage. The placeholder wordmark remains visibly provisional; no final logo is generated.

The toolbar has explicitly labelled native selectors for visual direction A/B/C, copy set A/B/C, and tagline (direction default or one of the six candidates). Show all current selections and a polite status update. Changing visual direction resets copy to the matching direction and tagline to default. Changing copy updates headline, description, process header, and its default tagline, resetting any tagline override. Changing tagline updates only that field. A direction-default tagline follows the selected copy set.

Keep the `miller-design-review` storage key and store only validated selection IDs. Restore recognized theme, copy, and tagline values on reload. Existing `{theme, tagline}` preferences migrate to matching copy and a recognized tagline ID; unknown display strings are discarded. Missing, malformed, primitive, or unavailable storage starts at A with A copy/default tagline. An invalid theme resets the complete selection to A; an invalid copy falls back to the valid theme, and an invalid tagline falls back to default. Failed reads/writes never break controls. Insert copy as text, never interpreted HTML. A remains the rendered and usable no-JavaScript default; controls explain that switching requires JavaScript when it is unavailable.

Keep an unmistakable Draft notice adjacent to the preview copy and in the toolbar. It must remain visible after every selection and identify factual claims as pending verification. Kit approval is permission to explore its copy; it is not Erik's final approval or substantiation of years, reviews, licensing, or performance claims.

Use touch targets at least as large as the existing 44px controls, visible focus, sufficient contrast, and responsive wrapping. Prefer a toolbar in document flow with optional desktop sticky positioning; avoid a fixed overlay that obscures content or keyboard focus. B2 must prove usability at 320px/390px and desktop 200% zoom, including long tagline choices. Meet applicable WCAG 2.1 AA criteria: keyboard access, labels, focus order/visibility, status announcements, text/non-text contrast, and reflow. Decorative palette values must not compromise these criteria.

## Brand-lock and build contract

Keep `docs/brand/brand-lock.json` as the canonical production input. Define schema version 1 with `direction`, `copyDirection` (each A/B/C), `taglineId` (default or a known candidate ID), `approvedBy` (Erik Miller), `approvedOn` (a real ISO calendar date), and `adr` (a repository-relative decision path). Reject missing/unknown fields, unsupported versions, wrong types, invalid selections/dates, and any approver other than Erik. Legacy direction-only locks require an explicitly approved migration; do not silently fill copy choices.

Resolve `adr` within `docs/architecture/decisions/`; reject traversal, absolute paths, escapes through symlinks, missing/unreadable files, and non-Accepted records. The decision record must carry a structured version-1 brand-choice metadata block containing the same direction, copyDirection, taglineId, approvedBy, and approvedOn. Its dated human approval note links the recorded Erik sign-off. Require exact agreement with the lock. Merely pointing at an Accepted stack/policy ADR, or writing nonempty approval strings, is insufficient. This is a repository audit gate, not cryptographic proof: Matt remains responsible for recording the actual sign-off accurately.

No real lock or choice record is created by MR-02. When Erik chooses later, add a separate brand-choice ADR under 0003 and record the actual evidence; normal ADR approval/amendment rules apply. BRAND-01 also requires the final mark, so a valid lock alone cannot close it or authorize launch. Later custom copy or a choice outside the approved catalog requires a contract amendment and evidence before the lock accepts it.

Use one build-time validation/selection owner consumed by the existing command and Astro page entry points. Browser code consumes review-only data; it never reads approval records. Production selects one visual direction, one four-field copy set, and one resolved tagline. The default tagline must not ship alongside an override unless the strings are identical. Production includes only Inter and the selected display font assets and one selected token set. Review labels/selectors, all alternative payloads, `data-theme` switching, storage/persistence code, and review-only CSS/JS are absent. Imports that copy unused assets into the output must be restructured rather than hidden at runtime.

Keep `npm run build`, `npm run build:web`, and ordinary development defaulting to review A. `npm run build:production` and a web build with `SITE_BUILD=production` must both enforce the canonical lock before rendering. Reject unknown modes and reject attempts to choose production using `BRAND_DIRECTION` or an arbitrary lock-path override. A bare environment mode such as `production-check` must not bypass validation. Preserve review publication settings and Worker dry-run behavior.

`npm run check:production` owns disposable verification builds. For A/B/C, stage a synthetic lock plus matching Accepted choice-record fixture in an isolated workspace/output boundary, validate through the same contract, build, and call the existing `verifyProduction(directory, direction)` seam. Synthetic records are explicitly labelled verification-only and cannot satisfy the canonical production path. Keep the real lock and ADRs unchanged, clean fixtures in a finally path, and report failures with nonzero exit status. Never copy a real lock into fixtures or claim their success as Erik approval. Ordinary commands cannot promote a fixture build to production.

Expand `verifyProduction` without removing its current checks. Inspect every output file: HTML/CSS/JS and textual data/maps/manifests for alternative tokens, copy, controls, and persistence; inventory binary assets and compare font/media ownership. Verify selected fields actually render. Use direction/choice-specific catalog values and build inventory, accounting for shared strings such as `--brand-paper`; absence of one marker is insufficient. Check override and cross-direction copy combinations as well as A/B/C defaults. Production failure must not leave a stale artifact tree that can be mistaken for a successful candidate.
